Kernel Benchmark
================

gemmstone comes with a built-in benchmark, `benchstone`, offering both functional and performance testing.


Preparing a Kernel for Benchmarking
-----------------------------------

Prior to running `benchstone`, the kernel needs to be prepared for benchmarking. Usually this is done via one of the `*prep.pl` (Linux) or `*prep.bat` (Windows) scripts, which call the appropriate `frontend` executable to generate the kernel and place the resulting kernel binary and *infofile* in a known temporary location for `benchstone` to read.

./prep.pl gemm SSS NNN 16 8 1 0

The kernel binary and infofile are stored in files `gemm.<userid>.{bin, note}` in the top-level temporary directory &mdash; `/tmp` (Linux) or `C:\Temp` (Windows).

> [!NOTE]
> `benchstone` can test non-gemmstone kernels too, as long as they use the gemmstone calling convention. You'll need to create the infofile by hand &mdash; a text form of the [`CommonDriverInfo`](../include/gemmstone/driver_info.hpp) struct. The kernel binary should be an OpenCL/Level Zero program binary as generated by e.g. `ocloc`.


Basic Usage
-----------

When not given any arguments, `benchstone` will run a standard suite of accuracy tests, and if all tests pass, performance tests for some large square sizes.

To control the type of testing, use the `-a` (accuracy) or `-p` (performance) flags. You can enable extra output with the `-v` (verbose) flag. For accuracy tests `-v` prints a line for each test case, while for performance tests `-v` enables extra statistics.

To test specific matrix dimensions, the syntax is:

    ./benchstone MxNxK      # A is MxK, B is KxN, C is MxN
    ./benchstone BxMxNxK    # for batched kernels

The dimensions may also be delimited by spaces instead of `x`. If you have multiple test sizes, consider using a [batch file](#batch-files).

To set the leading dimensions (strides between adjacent columns/rows), the syntax is

    ./benchstone [Bx]MxNxK lda ldb ldc      # "lda" = leading dimension of A, etc.

Some special values for leading dimensions are recognized:

* `0` means tight leading dimensions (no padding)
* `-1` means "nice" leading dimensions (well-aligned)
* `-2` means "bad" leading dimensions (worst-case alignment)

> [!IMPORTANT]
> By default `benchstone` uses nice leading dimensions. Most applications (unfortunately) use tight leading dimensions.

> [!TIP]
> Reminder: the kernels in the catalog are in column-major format. To convert a GEMM problem from row-major to column-major, swap $m$ and $n$, and A and B. For other level-3 kernels, additional changes may be needed, *e.g.* switching left/right and lower/upper.

> [!NOTE]
> Level-3 copy kernels only have two dimensions, so the syntax is a little different:
>
> `./benchstone MxN [lds ldd]`
>
> where `lds` and `ldd` are optional leading dimensions for source and destination matrices, respectively.

### Accuracy Testing

Most kernels have multiple paths (based on runtime checks for e.g. size and alignment). The default accuracy test suite includes tests to exercise these different paths, including:

* constant and random initialization
* m/n/k remainder handling
* beta = 0 special path
* badly aligned base addresses
* badly aligned leading dimensions
* badly aligned batch strides (batch kernels)
* complex conjugation for A/B
* (TRSM) unit/non-unit diagonals
* (`trsm3`) in-place/out-of-place mode
* A/B/C offsets

If one of the default tests fails, `benchstone` will print a one-line summary of the failing test case. With `-v`, or if you provide a specific size for testing, an entry-by-entry comparison of inaccurate elements will be printed, up to a maximum of 100. You can increase this maximum with the `MAX_INACCURACIES` environment variable.

In addition to the text output, `benchstone` will also dump the computed and reference output matrices to the current working directory for examination as raw binaries (`computed.bin` and `ref.bin` respectively). A quick Matlab script ([bmerror.m](../tools/matlab/bmerror.m)) is available for plotting the results:

```
>> cd gemmstone\build\matlab
>> bmerror
```

#### Optional Testing Kinds

`benchstone` supports several additional testing kinds that are not enabled by default. They are controlled by environment variables:

**4GB checks**: Under Level Zero, there is an additional option controlled by  `CHECK_CROSS_4GB`. When set to a nonzero value, `benchstone` will run additional tests with A/B/C allocations that cross a 4GB address boundary.

**Determinism checks**: If `CHECK_DETERMINISM` is set to a nonzero value, `benchstone` will run simple checks to see if a kernel produces deterministic output.

### Performance Testing

In performance testing mode, typical `benchstone` output looks like:

```
Using OpenCL device Intel(R) Data Center GPU Max 1100 (XeHPC, 1x56x8 = 448 EUs, 1550 MHz).
Testing kernel gemm SSS NNN 64 32 1 0
Size is 1024 x 1024 x 1024, leading dimensions 1056, 1056, 1056
              Blocking: 1024x1024x1024, 1x1x1 blocks
          Thread group: 4x8x1 (?x-x-)
               Slicing: 4 WGs in m dimension sliced into 1x4-wide slices
    Variable k-slicing: slicing final 16 group(s) with k chunk size = 304
          Average time: 115.44us (6 repetitions) -- std. deviation: 346.872ns
           Actual GB/s: 109.00
          Actual GOp/s: 18602.6
            Peak GOp/s: 22220.8
    Nominal efficiency: 83.7%
  Effective efficiency: 89.5%   (1450 MHz)
```

It shows:
* GPU name and information
* Matrix dimensions
* Workgroup and large-scale blocking configuration
* Configuration information for some specific algorithms (boustrophedon ordering, variable k-slicing)
* Average device times for warmup and timing runs, and standard deviation
* Average memory bandwidth
* Average compute throughput and compute efficiency
* Theoretical peak compute throughput

When available, `benchstone` uses MDAPI metrics collection to monitor frequency and provides average frequency and effective compute efficiency (efficiency computed relative to actual frequency, rather than nominal frequency), as shown in the example above.

Additionally, verbose mode (`-v`) shows:
* Warmup time
* Host overhead (difference between host time and device time)

By default, `benchstone` executes 2 warmup runs, then 6-8 timing runs, with fully-random data. You can control iteration count with the `WARMUP_REPS` and `TIME_REPS` environment variables.

Default testing is warm-cache &mdash; reusing the same memory for each test iteration. You can switch to cold-cache testing by setting the environment variable `COLD=1`.

> [!NOTE]
> `benchstone` implements cold-cache testing by executing a "flush kernel" between test runs. On XeHPG and later GPUs, the flush kernel works by targeted eviction of A/B/C cache lines (with LSC uncached prefetches); on earlier GPUs, it reads a large amount of dummy data through cache.

> [!NOTE]
> For Linux users: MDAPI metrics collection requires the MDAPI library to be installed (not always provided with driver packages). Superuser privileges are also required unless `i915.perf_stream_paranoid` is set to 0. `benchstone` will provide hints where possible on resolving any issues it finds when attempting to collect metrics.

### Supported Kernel Types

Benchstone supports most kernels that can be generated by the frontend. There are a few exceptions/restrictions:

* Non-constant offsets are not supported yet.
* Non-strided batch kernels (`batchn`) are not supported under the OpenCL runtime, since it uses OpenCL buffer objects to store data. The Level Zero version of `benchstone` does support `batchn`.
* Span batch kernels (`batchnv`) are not supported.

### Kernel Progress Tracing

If the kernel was created with [tracing enabled](frontend.md#kernel-progress-tracing), `benchstone` will output the tracing data to a file named `gemm_trace.json` in the current directory for visualization with [Chrome tracing](chrome://tracing).

List of Controls
----------------

`benchstone` supports a large number of environment variable options, listed in the following sections.

### Fill Values

When debugging both accuracy and performance issues, it is often useful to control how matrix data is initialized. `benchstone` offers several different fill patterns that are configured by environment variable:

    <MATRIX>=<FILL TYPE>

where `<MATRIX>` is one of `A`, `B`, `C`, `A_SCALE`, `B_SCALE`, or `CO` (C offset), and `<FILL_TYPE>` is one of:

* `ZERO`, `ONE`, `ONE_HALF`: constant values.
* `RANDOM`: random values, uniformly distributed in $[-1, 1]$.
- For complex data types, random values are taken uniformly from the unit disc.
- For TRSM kernels, random values for A/B matrices are chosen carefully to avoid ill-conditioning and facilitate accuracy testing.
* `ROW_RAMP`: all entries in row $i$ (1-based) are set to $i$.
* `COL_RAMP`: all entries in column $i$ (1-based) are set to $i$.
* `ROW_STRIPE`: one row is set to 1 and the rest of the matrix to 0. The location of the all-1s row is configured by the value of the environment variable `STRIPE_INDEX`.
* `COL_STRIPE`: similar to `ROW_STRIPE` but for columns.

It's also possible to load A/B/C matrix data from disk. To do this, set the environment variable `DATA_PATH` to a folder containing files named `A.txt`, `B.txt`, and/or `C.txt`. Matrix data is expected to be in text format, with entries delimited by whitespace or commas.

### Scalar Variable Overrides

* `ALPHA=<value>`, `BETA=<value>`: set alpha/beta values, if the kernel supports runtime alpha/beta selection.
* `AO=<value>`, `BO=<value>`: set A/B constant offsets, for `offseta`/`offsetb` kernels.

### Kernel Configuration

* `M_BLOCKS=<n>`, `N_BLOCKS=<n>`, `K_BLOCKS=<n>`: break up the GEMM problem into the given number of blocks in the m/n/k dimensions, respectively. Each block is a separate kernel launch.
* `FIX_WG_K=1`: disables automatic adjustment of the k workgroup size.
* `PERSISTENT_GROUPS=<n>`: set the number of workgroups launched for a persistent threading kernel.
* `K0=<n>`: set k block size to `n`, for k-parallel kernels.

#### Variable k-Slicing (Stream-k) Controls

* `K_SLICED_WAVES=<n>`: apply variable k-slicing to the last `n` waves at most.
* `K_SLICED_TILES=<n>`: apply variable k-slicing to the last `n` workgroup tiles of C.
* `K_SLICED_PHASES=<n>`: divide variable k-sliced region into `n` separately-balanced phases. Possible values: 1, 2.
* `K_SYNC_SLABS=<n>`: use `n` k-synchronized slabs in each variable k-sliced phase.

### Memory Options

* `A_OFFSET_ELEMS=<n>`, `B_OFFSET_ELEMS=<n>`, `C_OFFSET_ELEMS=<n>`: set starting offset in memory for A/B/C matrices from the beginning of their memory allocation.
* `ODD_LDAB=1`: Force odd leading dimensions for A/B (useful when `benchstone` is launched from another tool).

### Performance Testing Options

#### Timing Options

* `WARMUP_REPS=<n>`: set the number of warmup iterations before recording times.
* `TIME_REPS=<n>`: run exactly n timing iterations.
* `TIME_MIN_REPS=<n>`: run at least n timing iterations.
* `TIME_MAX_REPS=<n>`: run at most n timing iterations. Fewer iterations may be run if timing is sufficiently stable.
* `SHOW_ALL_TIMES=1`: show device times for each kernel launch.

#### Metrics (Performance Counters) Options

* `EXTRA_METRICS=1`: Report additional metrics where available, e.g. L3/main memory traffic, cache usage.
  - `METRIC_SET=<name>`: Choose a custom metric set (default: ComputeBasic), e.g. for collecting TLB or I$ metrics.
* `ENABLE_METRICS=0`: Disable MDAPI metrics collection (including frequency monitoring). By default it is enabled for performance testing, but may be disabled in case of driver bugs.

#### Cache Options

* `COLD=<spec>`: control cold-cache testing. Several options are available:
  - `COLD=1`: evict all buffers from the cache hierarchy prior to each kernel launch.
  - `COLD=[A][B][C]`: select a subset of A/B/C buffers (e.g. `COLD=AC`) to evict.
  - `COLD=I`: flush instruction cache prior to each kernel launch.
  - `COLD=T`: flush TLB prior to each kernel launch.
* `CACHE_FILL=1`: fill LLC with dirty data prior to each kernel launch.


### Functional Testing Options

* `ALPHA=<val>`, `BETA=<val>`: choose alpha/beta values, for kernels with runtime-configurable alpha/beta.
* `AO=<val>`, `BO=<val>`: choose A/B offset values, for kernels with scalar A/B offsets.
* `MAX_INACCURACIES=<n>`: choose how many inaccurate results will be displayed before output is truncated.

### Runtime Setup

* `IN_ORDER`: (OpenCL) If set to any value, use an in-order queue (default is out-of-order).
* `IMMEDIATE={0,1}`: (L0) Disable/enable immediate command lists (default: disabled).
* `TIMESTAMP_EVENTS={0,1}`: (L0) Disable/enable kernel timestamps for device timing (default: enabled).
* `DEVICE_MEM=<n>`: (L0) Set memory ordinal to use for device memory allocations.
* `PLATFORM=<n>` (OpenCL) Use the `n`th GPU platform, zero-based (default: 0).
* `DRIVER=<n>` (L0) Use the `n`th GPU driver, zero-based (default: 0).
* `DEVICE=<n>` Use the `n`th GPU device, zero-based (default: 0).
* `TILE=<n>`: (L0) Use the `n`th subdevice/tile for kernel execution.
* `MEM_TILE=<n>`: (L0) Allocate memory on the `n`th subdevice/tile.
* `CARD=<n>`: (Linux) set the DRM card index for this device.

### Device Overrides

* `GEN=<prefix>`: Override automatic detection of the GPU type. `<prefix>` should be one of the standard gemmstone GPU prefixes (e.g. 12p7).
* `FREQ_OVERRIDE=<MHz>`: Override GPU nominal frequency (useful on early HW, if the driver stack does not yet report frequency).
* `EU_OVERRIDE=<n>`: Override EU count in case of inaccurate information from driver.
* `MEMORY_BW=<GB/s>`: Provide peak main memory bandwidth. When provided, benchstone will report memory BW efficiency with respect to this peak.

### Debug Options

* `DISPATCH_INFO`: If set to any value, local and global work size information will be printed for each kernel submission.

Batch Files
-----------

`benchstone` can read a list of sizes for performance testing from a file. Each line of the file should have the following format:

    batch_size M N K lda ldb ldc

Leading dimensions are optional, and default to -1 (nice leading dimensions) if not provided.

In quiet mode (`-q`), batch mode output is in CSV format for easy parsing or data import.

Server Mode
-----------

`benchstone` supports a special *server mode* for communicating with other tooling (`pvc_derby`, remote GUI). In server mode, `benchstone` takes commands from a client, performs benchmarking as requested, and reports performance data back to the client. Instead of relying on a prepared kernel, the benchstone server interacts directly with `ofrontend` to generate kernels as requested by the client.

GUI Client
----------

`benchstone` comes with a Matlab-based graphical interface (`bmclient`) that communicates with a `benchstone` instance on a remote Linux machine over a TCP socket.

To get started, on the remote machine run `remote_benchstone.sh` from within your build folder to start up the benchstone server and hook it up to port 12345 over TCP.

Then on the client machine, run [`bmclient`] from Matlab:

```
>> cd gemmstone/tools/matlab
>> bmclient
```

After a short startup period, the main window will appear:

![image](https://github.com/user-attachments/assets/70b51fc1-2616-48b3-9a97-cceafb450b02)

In the bottom right corner, there's a field for entering the remote host name and port. After filling this information in, type Ctrl-T to connect (or just run any operation). After a few seconds, the red circle should turn green, indicating a successful connection.

![image](https://github.com/user-attachments/assets/c1cd5038-1bab-4697-b04a-60ce7906e70f)

> [!TIP]
> Sometimes there are firewall issues when connecting to lab machines from a Windows laptop.
>
> In case the connection fails (and you've double-checked the hostname), try connecting to the remote machine first from another lab machine with `netcat`:
>
> `nc <hostname> 12345`
>
> Type Ctrl-D to close the connection, then restart the remote `benchstone` process and try to connect again.

Once the connection is successful, you can start adding kernels for benchmarking. Click the + button or type Ctrl-K to add a new kernel to the list, or use Ctrl-M to input multiple kernels at once. A dialog will appear, asking for a kernel strategy string. This string will be sent to the frontend -- see the frontend [documentation](frontend.md) for details.

After entering a kernel, it will be generated, and benchmarking will immediately begin. As data is received from the server, it will be displayed on the graph to the right.

> [!IMPORTANT]
> Don't interrupt the UI while benchmarking is running. Matlab has very limited support for multithreading in GUI applications, and interrupting ongoing work is likely to cause the connection to be lost, or corrupt gathered data.

The next sections provide more details on the interface.

### Graph Panel

On the right, the graph panel displays benchmark results for all selected kernels. This is an interactive Matlab graph, supporting all the usual operations: zooming/panning/etc.

The drop-down boxes below the graph allow you to change what kind of data is collected:

* **Data Set**: problem sizes to benchmark. A number of sweeps are available, and more can easily be added by editing the Matlab source.
* **Leading Dimension**: controls leading dimension (good, tight, bad). "Tight" means no padding. The default "LD Range" setting will benchmark both good and bad leading dimensions for each problem size and displays the performance range.
  - In the example above, the blue kernel shows low LD sensitivity (good and bad have roughly the same performance), while the orange kernel's performance is much more sensitive to leading dimension.
* **Nominal/Effective**: controls whether nominal or effective efficiency is shown in the graph. Like usual, effective efficiency requires metrics collection to be working on your system.
* **Warm/Cold**: control cache mode.
* **Graph Type** (Line, Line w/ Max, Scatter w/ Max): controls how data is visualized -- only applies when a single leading dimension is displayed (good, tight, or bad). The "Max" modes will show a color-coded line tracking the kernel with best performance for each problem size.

As soon as any of the drop-down boxes changes, the GUI will immediately start collecting and displaying the new data set for all selected kernels. Note that all collected data is saved for later, and the GUI will reuse previously-benchmarked data for speed. You can select *View > Refresh Data* (Ctrl-R) to force data to be recollected for the current view.

In the snippet below, we've changed to a smaller size range, good leading dimensions, and used the Scatter w/ Max setting to highlight the best performer:

### Kernel Panel

The left panel holds a color-coded list of kernels under consideration.  You can check/uncheck kernels in the list to show/hide them in the graph, and add/delete kernels at any time.

Right-clicking a kernel in the list will bring up some additional options, including:s

* *Copy to Clipboard*
* *Modify Kernel*: brings up the Add Kernel dialog with the current strategy already filled in, for quick tweaks

In a large tuning project, once you've accumulated a large list of good kernels, you may want to copy all your strategies to the clipboard. *Kernel > Copy All Selected Kernels* will do exactly that.

### Other Operations

You can save to/restore from disk the full set of data collected using the operations from the Data menu.

In case of errors, the GUI will display an appropriate error dialog. Some catastrophic issues (e.g. GPU hangs) may cause the connection to the remote benchstone server to be lost. This will be reflected by a red circle in the lower-right corner. If that happens, just restart the benchstone server on your remote machine and go to *View > Reconnect* (Ctrl-T) to bring the connection back up.
