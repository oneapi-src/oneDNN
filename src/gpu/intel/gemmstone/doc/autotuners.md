Autotuning Tools
================

gemmstone includes several autotuning tools to automatically identify high-performing kernel strategies:

* **multiderby**: a flexible autotuner that can tune a single kernel for a single problem size, or multiple kernels to cover a range of problem sizes.
* **pvc_derby**: seeks the best kernel in a class of candidate kernels that all target the same range of problem sizes.

Multiderby is the successor to pvc_derby and should be the first choice in most situations.

If you are new to gemmstone's strategy options and strategy text format, start by looking at the [frontend documentation](frontend.md).


Using Multiderby
----------------


### Setup

Multiderby needs to know the rough global memory bandwidth of your GPU to do its work. You can use a tool like clpeak or BabelStream for this, though beware of memory compression on Xe2 and later GPUs.

Once you identify the memory BW (in GB/s), set the `MEMORY_BW` environment variable to inform multiderby (and `benchstone`) about it.


### Example Command Lines

Search for a set of NT SGEMM kernels to cover the full range of GEMM problem sizes. Multiderby automatically selects a set of sizes to test:

```
./multiderby gemm SSS NTN
```

Search for a set of NN bfloat16 GEMM kernels to cover compute-bound sizes (`-pc`) for 16-byte-aligned inputs:

```
./multiderby -pc gemm BBS N@16N@16N
```

Search for memory-bound int8 TN compressed weights kernels:

```
./multiderby -pm gemm OHS T@4N@4N
```

Search for ZGEMM kernel(s) covering two particular sizes of interest (`-p MxNxK`):

```
./multiderby -p 2048x2048x2048 -p 2048x1536x2048 gemm ZZZ NNN
```

If you have many problem sizes to pass to multiderby, there is a `-pf` option for reading problem sizes from a file.

> [!NOTE]
> Multiderby doesn't perform any accuracy testing on generated kernels. Be sure to check accuracy before putting the generated kernels into production.


### Progress Display

Once started, multiderby will continuously generate kernels and benchmark them. For details on its search and optimization methodology, see [the multiopt documentation](algorithms/multiopt.md).

Autotuning can be a lengthy process, so multiderby displays frequent updates while running, showing the current status, top kernel selections, best- and worst-performing problem sizes, etc.

Packed at the top, you can find:
* Amount of time remaining (multiderby defaults to running for 2 hours &mdash; adjustable via the `--time-limit` option)
* Number of problem sizes under consideration
* Number of strategies benchmarked
* Total number of data points (individual benchmark runs)
* Success rate in generating viable kernels
* Average kernel efficiencies:
  - `abs`: efficiency with respect to a simple memory/compute roofline model
  - `eff`: efficiency with respect to multiderby's autogenerated roofline model (see [Rooflines](#rooflines) for more information)

Below these lines are the current set of _selected strategies_. Multiderby aims to find a minimal set of strategies that provide sufficient performance (>= 95% of best observed performance) on all the problem sizes it is benchmarking. The chosen set of strategies is updated periodically, or you can press `s` to manually trigger the selection process. This area will be empty at the beginning of autotuning, when insufficient data is available.

At the bottom, multiderby lists its best and worst performing problem sizes, along with the best strategies found for each. In the example here it has found near-100% performance for large compute-bound SGEMMs, as expected, but low performance for the smallest GEMMs, which are overhead/latency-bound.

> [!NOTE]
> At the very beginning of the session, you will see "collecting initial data" near the top of the screen. In this process, multiderby is trying to estimate the relative impact of different strategy parameters. Sometimes, this step can fail to complete, meaning that multiderby was unable to successfully generate a kernel with some particular strategy option. In the future, there should be a timeout for this step.


### Rooflines

Roofline models are important for multiderby's optimization process. Multiderby uses rooflines as targets for kernel performance, spending more time on problem sizes that are farther from the roofline.

At the beginning of an autotuning session, multiderby starts with a basic roofline (the "absolute" roofline), a standard roofline based on the GPU's main memory bandwidth and the compute throughput. As autotuning proceeds, multiderby uses the performance data it has acquired to generate an "effective" roofline &mdash; an empirical model based on the best performance achieved by any of the strategies it has seen so far. Multiderby blends the absolute roofline with the empirical model to generate its current roofline, gradually placing more and more weight on the empiricial model as it collects more data.

After autotuning has completed, multiderby saves its data store to disk (use the `-o` option to override the default path). Later you can query the effective roofline model for a particular problem size using the `-r` option to understand how fast multiderby thinks that problem can run:

```
./multiderby -o my_data -pc gemm QQS NNN       # previous session
...
./multiderby -i my_data -r 2000x1500x300       # how fast should this GEMM run?
```


### Finishing Up

By default, multiderby completes as soon as it hits its 2-hour time limit. You can quit earlier by pressing `q`, or adjust the time limit with the `--time-limit` option -- for instance, for a single problem size, 10-15 minutes is probably sufficient.

At the end of a run, multiderby by default prints its current set of selected kernels (if any) and saves all benchmark data to disk, where it can be loaded later (with `-i`) for future runs.

You can also use the `-k` option to write the selected kernels to disk, and `-o` to choose the filename for output data.


### Checkpoints

In case of any issues (crashes/hangs, reservation ending, accidental Ctrl-C, etc.), multiderby periodically writes checkpoint files to disk. Multiderby can restart from these checkpoints automatically if you run it again with the same command line.


### Autotuning Tips

* If you are tuning for a particular problem size, it can still be helpful to provide multiderby a larger set of similar problem sizes, so it can ensure your strategy also works well on similar sizes.
  - Some strategies exhibit "fragile" performance -- fast for some problem sizes, slow for nearby problem sizes. These should almost always be avoided in production. Strategies with smaller workgroup sizes are more prone to this behavior -- when there are multiple workgroups per XeCore, performance becomes much better if these workgroups happen to share A and/or B data out of L1$.
* For complex dequantization scenarios (e.g. grouped scales/zero points), it's recommended to provide your quantization settings to multiderby, e.g.

```
./multiderby -pf my_problem_sizes.txt offseta[g32] scalea[g32] gemm FHS T@16N@16N
```

Using a small group size (here 32) is also recommended, as these small group sizes can increase register pressure.



Using `pvc_derby`
-----------------

`pvc_derby` is another powerful autotuner, with a slightly different focus from multiderby. Its goal is to find the best kernel from a *class* of candidate kernels.

For `pvc_derby`, a class of kernels is defined by its "XeCore tile size." If the strategy's workgroup size is such that one workgroup fills an entire XeCore (e.g. `wg 4x8 grf256` for PVC/Xe2), the XeCore tile size is just the workgroup tile size. If $W$ workgroups fit in an XeCore, we say the kernel has an XeCore tile size of MxN if we can assemble $W$ workgroup tiles to make an MxN tile.

The XeCore tile size is a useful metric for comparing kernels: if two kernels have the same XeCore tile size, they directly compete for the same problem sizes. That's because a given problem size will fill the same number of XeCores with both kernels, mostly eliminating performance differences due to load parallelization/balancing and focusing on performance differences due to per-XeCore efficiency.

`pvc_derby` automatically chooses an appropriate set of problem sizes to benchmark, depending on the given XeCore tile size. However, this can be overridden with the `INPUT_FILE` environment variable, providing a file with a list of problem sizes to use.


### Starting `pvc_derby`

`pvc_derby` syntax looks much like the start of a regular kernel strategy, but with XeCore tile sizes in place of per-thread tile sizes:

```
./pvc_derby gemm DDD NNN 128 64 1 0
# 128x64 = XeCore tile size
# alpha = 1, beta = 0
```

`pvc_derby` does not automatically search systolic strategies. Add `sys` to the command line if you are looking for this:

```
./pvc_derby gemm TTS T@8N@8N 256 192 1 0 sys
```

More generally, you can add any desired strategy specifiers to the end of the command line, if `pvc_derby` does not automatically look for them.
Commonly-used additions include:

* `sys`: enable systolic array
* `dot`: dot-based kernels
* `ska`: full k-split prefetch for matrix A (particularly for memory-bound NN kernels)


### Progress Display

`pvc_derby` runs a sequence of three kernel screening phases, then a final performance and accuracy check for the top 20 kernels found.

The first phase is designed for speed, with limited benchmark runs per strategy. In subsequent phases, `pvc_derby` tests more problem sizes and increases the number of iterations when benchmarking for more accurate performance results.

> [!NOTE]
> For speed, `pvc_derby` only performs accuracy checking at the end of autotuning.


### Finishing Up

At the end of the run, `pvc_derby` prints a sorted list of kernel strategies to `stdout`, which you can redirect into a file for safekeeping.


### Environment Variable Options

`pvc_derby`'s behavior can be controlled by a number of environment variable options:

General autotuning options:
* `MEMORY_BOUND=1`: autotune a memory-bound kernel. Performance is shown in GB/s and `THIN` is automatically assumed.
* `THIN=1`: autotune a thin-tile kernel. The smaller of m/n XeCore tile sizes is also used for the full matrix size.
* `COLD=1`: same syntax as [benchstone](benchstone.md)'s option: sets cold-cache mode for benchmarking. You can also use `COLD=A`, `B`, `C` to restrict cache eviction to certain matrices.
* `SCREEN_TIME=n`: set time per screening phase to `n` seconds. Each `pvc_derby` run has 3 screening phases.

Options controlling generated kernels:
* `TRY_SLM=1`: allow SLM pipelines even if not absolutely required for decent performance.
* `FORCE_COPY_A=1`: always copy A through SLM
* `FORCE_COPY_B=1`: always copy B through SLM
* `MODEL=s`: use surface accesses (pre-PVC only) instead of A64 accesses.
* `MAX_WG_K=n`: limit the number of threads per WG in the k dimension to `n`.
